# Hiking Planner — архитектура (ADR baseline, 18.11.2026)

## 1. Архитектурные принципы

1. **Solo-first**: один пользователь и один личный комплект данных; групповые сценарии не влияют на базовый интерфейс.
2. **Local-first**: все созданные пользователем данные хранятся на устройстве в IndexedDB; интернет — источник дополнительных сведений, а не условие функционирования.
3. **Один источник истины**: первичные сущности хранятся, итоги вычисляются; данные разных походов не смешиваются.
4. **Внешние сведения не равны подтверждённым**: source/provenance, retrievedAt, licence, reviewedAt, confidence/status.
5. **Без обязательных платных сервисов, аккаунтов и сервера** на первом этапе.
6. **Честные ограничения**: нельзя обещать универсальный поиск соцсетей, офлайн-тайлы из публичного OSM или точный прогноз на произвольную будущую дату.

## 2. Предлагаемый технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| UI | React + TypeScript (strict) + Vite | Разделение экранов, типизация и быстрая локальная сборка |
| Маршрутизация | React Router | Адреса разделов и переходы между походами |
| Стили | CSS custom properties + CSS modules (при необходимости) | Самостоятельная дизайн-система без привязки к монолитному HTML |
| Состояние UI | React hooks / локальные хуки; дополнительный state manager только при доказанной потребности | Меньше зависимостей |
| Локальная БД | IndexedDB + Dexie | Индексы, транзакции, версии схемы, офлайн |
| Валидация ввода | Zod или эквивалентная схема | Гарантии формата импортируемых/пользовательских данных |
| ГИС | Leaflet + OSM-совместимые подложки, GPX/GeoJSON | Простой и понятный картографический редактор для MVP |
| Геоданные | GeoJSON для геометрии, lat/lon WGS84, GPX для обмена | Интероперабельность |
| Тесты | Vitest + React Testing Library + Playwright | Бизнес-расчёты, UI, критические сценарии |
| Excel | библиотека импорта/экспорта XLSX после проверки форматов и условий использования | Excel как вход/выход, а не основная БД |
| PDF/печать | браузерный print + отдельный PDF-экспорт на позднем этапе | Контролируемая вёрстка |

Версии зависимостей закрепляются в lockfile при первом создании рабочего каркаса. Конкретные версии не придумываются на стадии документации; при реализации устанавливаются актуальные совместимые релизы.

## 3. Логические слои

```text
src/
  app/                 # инициализация, маршруты, провайдеры и оболочка
  pages/               # Походы, Поход, Карта, Меню, Снаряжение, Библиотека...
  features/            # create-trip, edit-menu, add-product, import-gpx...
  entities/            # модели, хранилища, простые представления сущностей
  domain/              # чистые вычисления и проверки, не зависящие от React
    calculations/      # масса, БЖУ, упаковки, бюджет, календарь
    rules/             # предупреждения и правила готовности
  data/
    db/                # Dexie schema + миграции
    repositories/      # CRUD + транзакции и запросы к IndexedDB
    importers/         # XLSX, JSON, GPX, GeoJSON
    exporters/
  integrations/
    providers/         # каждый внешний API имеет отдельный адаптер
    normalization/     # преобразование внешнего формата во внутренний draft
    cache/             # кэш, отметки актуальности, TTL
  shared/
    ui/                # кнопки, формы, карточки, диалоги, таблицы
    lib/               # дата/время, единицы, форматирование
    styles/            # токены и адаптивная дизайн-система
  test/
```

Это ориентир, а не требование создавать пустые каталоги до появления работающих модулей.

## 4. Передача данных и независимость модулей

```text
[React UI]
   | commands / queries
   v
[Application features] ----> [Domain pure functions]
   |                                  ^
   v                                  |
[Repositories -> Dexie/IndexedDB] ----+
   ^
   | user-reviewed draft only
[External provider adapters]
   ^
[Weather / OSM / product / medicine / equipment / photos]
```

Интернет-адаптер выдаёт **черновик результата** с metadata, не записывает напрямую в постоянный каталог. Пользователь проверяет карточку и подтверждает импорт. Каталожный продукт имеет стабильный локальный идентификатор; поход содержит ссылки на него и снимки изменяемых параметров (например, выбранную фасовку и цену).

## 5. Источники данных и CORS

- Провайдер имеет функции поиска, получения детализации, нормализации и проверки доступности; поддерживает timeout/abort, лимитирование запросов, повтор только при временных ошибках.
- При отсутствии публичного API или при запрете браузерного CORS — показываем ссылку на источник и ручной импорт разрешённых данных. Не используем сомнительные прокси для обхода ограничений.
- Секретные ключи никогда не размещаются в Vite-коде, `VITE_*` или в публичных сборках.
- Если позднее понадобится сервер-посредник (CORS, секретные ключи, доступ по лицензии), решение выносится в отдельный ADR с причинами и стоимостью; пока не подключается.
- Источники, лимиты и правила лицензирования — в `DATA_SOURCES.md`.

## 6. Local-first, сохранение и резервные копии

- IndexedDB — основное хранилище. `localStorage` допускается только для мелких несекретных UI-настроек, не как основная БД.
- Миграции Dexie: каждый релиз с изменениями схемы повышает версию и сопровождается тестом миграции.
- Удаление связанной сущности: транзакция, предпросмотр последствий, при возможности мягкое удаление/корзина. Не оставлять «висячие» ссылки.
- JSON-бэкап включает `schemaVersion`, `exportedAt`, `applicationVersion`, таблицы и, в полном режиме, локальные пользовательские вложения.
- При восстановлении: проверка схемы, объёма, корректности идентификаторов и связей, предпросмотр, подтверждение и атомарная запись; не затирать текущие данные молча.
- Поскольку IndexedDB может быть очищена браузером, напоминать о резервных копиях. Облачная синхронизация не обещана.
- Offline-PWA в позднем этапе: cache-first для интерфейса; network-first с контролируемым кэшем для динамических источников. Заранее запретить несанкционированный prefetch картографических тайлов.

## 7. Вычисления — в чистых функциях

- Пищевая ценность порции: `valuePer100g * edibleGrams / 100`. Отличать сухую и готовую массу; вода для гидратации не умножает пищевую ценность.
- Масса закупки и масса переносимого запаса различаются; количество упаковок — целое округление вверх от нетто с учётом неполных остатков.
- Рюкзак: включённые предметы с положением `pack` и переносимые расходники, независимо от состояния упаковки. «На себе» — отдельная сумма. Потребление по дням уменьшает расходный вес только по явно заданной модели.
- Бюджет: целые минимальные денежные единицы + ISO 4217, без floating point в сумме; отсутствующий факт не трактовать как ноль.
- Дни и события: ISO calendar dates в маршруте, для расписаний timezone-aware timestamp + исходный часовой пояс или локальное время и IANA timezone; не полагаться на `Date.toISOString` для местной даты.
- Расстояния и набор/сброс — отдельно указать происхождение и метод расчёта; очищать выбросы высот и не выдавать интерполированный трек за измеренный.
- Все правила проверок выдают `pass / warning / fail / unknown` с обоснованием; неизвестные данные не должны приводить к ложному «всё безопасно».

## 8. UX-архитектура

- Десктоп: боковая навигация, основной контент, необязательная панель итогов; мобильный: нижняя навигация основных модулей, остальное через «Ещё».
- Локальный каталог — отдельный раздел «Библиотека». Добавление в поход производится выбором из библиотеки с возможностью создать запись на месте.
- Подробная карточка: обзор → параметры → источник и дата → действия. Не скрывать единицы измерения.
- Ошибки сети не блокируют формы. Все действия с массовой правкой показывают предпросмотр и имеют отмену.
- Цвет не является единственным признаком статуса. Статус сопровождается текстом/значком.
- Визуальный референс: Qwen HTML (палитра и блоки), но без наследования невалидного JS, несвязанных хардкодов и фиктивной SVG-карты.

## 9. Безопасность и приватность

- Походные координаты, история передвижений, контакты и медицинские записи потенциально чувствительны. По умолчанию остаются на устройстве.
- Не логировать персональные данные и полные резервные копии в консоли или GitHub Actions.
- В текстовых полях использовать экранирование; не вставлять описания из сети как сырой HTML. Удалять опасные HTML/скрипты из импортируемых файлов.
- Для картинок из интернета: ссылка и лицензия; перед кешированием проверить условия, избегать прямого копирования защищённого контента.
- Медицинский поиск: сохранять официальные инструкции и источники, отмечать устаревшие/непроверенные сведения, не генерировать схемы лечения как авторитетные рекомендации.
- Приложение не заменяет навигатор, аварийную связь, оценку местных рисков или медицинскую консультацию.
- При появлении API-ключей — только защищённое хранение на сервере-посреднике; пользователь может вручную настроить открытые ключи для личного использования лишь после отдельного решения по модели угроз.

## 10. Контроль качества

**Этап 0:** документация с взаимосогласованными решениями и критериями тестирования.  
**Этап 1 и далее:** каждый модуль поставляется с unit/e2e тестами и проверкой `npm run build`.  
**Перед релизом:** проверка офлайна, резервного восстановления, поведения при недоступных API, мобильного экрана, прав доступа к данным и отображения единиц измерения.

В `docs/PROJECT_STATE.md` фиксируем реальный HEAD/коммиты, выполненные проверки и точное следующее действие. Никаких утверждений об успешных тестах, пока они фактически не запущены.

## 11. Архитектурные решения для будущего (не включены)

Аутентификация, Supabase или собственный backend, CRDT и синхронизация, совместное планирование, push-уведомления, коммерческие каталоги и офлайн-векторные карты. Введение каждого требует отдельного решения, бюджета и тестов.
