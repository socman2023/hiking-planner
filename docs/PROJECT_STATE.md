## 2. Реализовано в коде

### База и доменная логика

- React 19, TypeScript strict, Vite, React Router, стили и адаптивная навигация.
- Dexie IndexedDB `hiking-planner`: schema v1 — `trips`, `days`, `settings`.
- Сущности `Trip`, `TripDay` и базовые типы статусов/активностей.
- Создание похода от 1 до 365 дней и генерация дневных записей.
- Сдвиг дат в UTC-safe календарной арифметике, сохранение порядка и данных дней.
- Изменение количества дней, удаление последних дней с проверкой последствий в UI.
- Изменение статуса, копирование независимого похода, удаление и транзакционная очистка его дней.
- Чистые date/validate функции, тесты високосного года.

### Интерфейс

- Русскоязычная оболочка «Hiking Planner» (случайное название референсного прототипа не используется).
- Стартовый экран: статистика, поиск, фильтрация и карточки походов.
- Форма создания и редактирования; обзор отдельного похода; календарь и редактирование каждого дня.
- Настройки и резервное копирование.
- Адаптация для десктопа и мобильного браузера. Разделы будущих этапов показывают **честные заглушки**, а не фиктивные данные.

### Резервные копии

- Формат `hiking-planner-backup`, schemaVersion=1, `exportedAt` и наборы `trips/days/settings`.
- Проверка формата, размера, идентификаторов, связанных дней и дат перед восстановлением.
- Подтверждение **полной замены** данных, запись транзакцией.
- Перенос походов между браузерами возможен через JSON. Автоматической синхронизации нет.

### Тестирование и CI

- `src/domain/trips.test.ts`, `src/data/tripRepository.test.ts`: 11 пройденных тестов.
- `tests/trips.spec.ts`: браузерные сценарии создания/правки/копирования и бэкапа, desktop/mobile.
- GitHub Actions: npm, TypeScript, unit, production build, Playwright Chromium. Начальный `package-lock.json` получен после успешной сборки.
- Проверка `npm ci` на последующих запусках CI предусмотрена: workflow выбирает `npm ci`, если lockfile существует.

## 3. Что НЕ реализовано

- Нет постоянных каталогов продуктов, блюд, снаряжения, медикаментов, треков, объектов.
- Нет меню и калорийных расчётов; нет карты, GPX, реальной погоды, интернет-поиска и транспортных/бюджетных расчётов.
- Нет PWA/offline service worker: локальная БД доступна, пока интерфейс загружен; закрытый сайт не гарантированно откроется без сети.
- Нет облачной синхронизации, групповых функций, мобильного нативного приложения, аккаунтов пользователей.
- Нет прямой визуальной проверки приложения пользователем; браузерные E2E-тесты подтверждают действия, не дизайн на всех реальных устройствах.
- Нет подлинного исходного .xlsx для точного сопоставления импорта по ячейкам. На него нельзя подменой выдавать демонстрационные данные HTML.

## 4. Известные ограничения и риски

1. В этапе 1 максимальная длительность ограничена 365 днями, чтобы не создавать необоснованно крупные базы. При необходимости лимит пересмотреть.
2. При сокращении длительности подтверждается **необратимое удаление** оставшихся календарных дней; отдельной корзины/undo пока нет.
3. Восстановление JSON в этапе 1 — **полная замена**, а не слияние. Перед восстановлением делать резервную копию.
4. Изображения и документы пока не входят в резервные копии: сущности MediaAsset ещё не реализованы.
5. Хранение зависит от браузерного профиля и квот IndexedDB; рекомендуется регулярно скачивать резервные файлы.
6. На начальной стадии нет полноценной установки офлайн/PWA. Не обещать запуск из браузера без сети после закрытия вкладки.
7. Интеграция внешних API требует проверки CORS, политики кэширования, лицензии и возможных региональных ограничений перед включением.
8. Правильная модель данных последующих модулей определена в `DATA_MODEL.md`, но не следует преждевременно создавать пустые таблицы.
